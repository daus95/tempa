Writing a Specification

What to put in the PRD you upload in Step 1, so Tempa spends less time asking clarifying questions and more time building.

What it is

Your specification (PRD) is the description of the new work you want Tempa to build: what it does, for whom, and roughly how. Tempa reads it during clarification (to find ambiguity), during planning (to lay out epics/features/tasks), and during implementation (as the source of truth for what "done" means.)

Only the new work goes here. This is not a place to describe the system as it already exists — that lives separately in sources.docs (the docs/ folder), and planning reads it automatically as context so it doesn't re-plan work that's already done. Writing already-implemented behavior into the PRD just gives Tempa more to (mis)read as new work.

You can use more than one file

The PRD isn't limited to a single file. Upload as many documents as you need — Tempa reads every file in the specification folder together during clarification and planning. Splitting a large specification into a few focused files (e.g. one per major area) is completely fine and often easier to write and review than one huge document.

The five things a good specification covers

Every specification that has worked well with Tempa covers these five aspects. The more completely each is written, the fewer clarification rounds you'll need before implementation can start.

1. Purpose

What problem does this solve, and for whom? State the audience and any hard constraints up front — "client-side only, no backend" or "internal tool, single admin user" changes what a correct implementation looks like more than almost anything else you'll write.

2. Business Process / Usage Flow

Walk through the actual sequence of steps a user takes, screen by screen or action by action. Number them. Call out validation rules and edge cases explicitly instead of assuming they're obvious — "down payment must not exceed the property price" is the kind of rule Tempa otherwise has to guess at, and it will ask you about it if you don't state it.

3. Data Model

List the main entities and their fields, and how they relate to each other. It doesn't need to be a formal ERD — a plain list of entities with their fields and relationships is enough, though an ERD is welcome for anything with more than a few related entities.

4. UI Concept

Describe the layout: what's on screen, how it's arranged, what changes on mobile vs. desktop. You don't need mockups — a written description of the sections/components and how they're arranged is enough for Tempa to build a reasonable first pass.

5. Tech Stack

Name the language, framework, and database (or explicitly "no backend/no database" if that's the case) you want used. Leaving this blank doesn't skip a decision — it just means Tempa (or clarification) picks one for you.

Two more sections worth adding

Not strictly required, but both consistently cut down on clarification questions:

Non-Goals

What's explicitly out of scope. "No user accounts", "no multi-currency support", "no real-time data sync" — stating what you don't want prevents Tempa from adding it "for completeness."

Acceptance Criteria

A few concrete input → expected-output examples. These double as a sanity check during QA: "property price 300,000, down payment 20%, 10-year term, flat method → principal installment 2,000/month" is unambiguous in a way that prose usually isn't.

What this looks like end to end

# PRD — <Feature or App Name>

## 1. Purpose
<problem solved, for whom, any hard constraints>

## 2. Business Process / Usage Flow
1. <step>
2. <step, with validation rules called out>
...

## 3. Data Model
- **<Entity>**: field, field, field
- <relationships between entities>

## 4. UI Concept
<layout description: sections, arrangement, responsive behavior>

## 5. Tech Stack
<language, framework, database — or "no backend" if that's the case>

## 6. Non-Goals
- <explicitly out of scope>

## 7. Acceptance Criteria
1. Input: ... → Expected: ...

This is exactly the structure used by both worked examples shipped with Tempa — see examples/ in the repo.

Just want to try Tempa first?

You don't have to write a specification from scratch to test-drive Tempa. The examples/ folder ships two ready-to-use sample PRDs — a simple client-side calculator and a full web app with a database — written following exactly the structure above. Upload one via Add File on the Upload Specification step, or copy it straight into the PRD folder, and go straight into clarification with a specification that's already in good shape.

Common mistakes

  • Including the existing system. Describing how the app already works belongs in docs/, not the PRD — the PRD is only the delta you want built.
  • Leaving validation rules implicit. "Obviously" a percentage can't be negative — but if it isn't written down, expect a clarification question about it.
  • Skipping the tech stack "because it doesn't matter yet." It always gets decided one way or another — deciding it yourself is faster than a clarification round.
  • One giant wall of text. Structure it under the headings above (or split across a few files) — an unstructured PRD produces more, vaguer clarification findings.
  • Writing project-wide rules here instead. Standing decisions that apply to every feature (database choice, API error shape, code-quality bars) belong in Architecture Principles, not repeated in each specification.

Where it goes

Specification files live in the working folder you selected, in the PRD folder:

<your-working-folder>/.tempa/specs/prd/

Upload files there with Add File/Add Folder on the Upload Specification step, or drop them into that folder directly and click Refresh. Once uploaded, continue to Clarification to have Tempa check for anything ambiguous before implementation starts.
