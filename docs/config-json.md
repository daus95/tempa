# `config.json` Structure

See [README.md](../README.md) for a summary. Full reference for every key in `config.json`.

`config.json` lives inside the **active workspace**, at `<workspace_root>/.tempa/config.json` —
not inside Tempa's own install folder. Each workspace keeps its own copy, so switching
workspaces (`tempa close-folder` + `tempa init <other_path>`) never overwrites another
workspace's settings/history. Before any workspace is active, Tempa falls back to a scratch
copy at `<tempa_install>/.tempa/config.json`. See
[folders-and-paths.md](folders-and-paths.md) for the full mechanism.

| Key | Purpose |
|-----|--------|
| `workspace` | Working folder (root + docs/adr/specs/apps/infra/archive) — see [folders-and-paths.md](folders-and-paths.md) |
| `sources` | Input/output paths for each command, derived from `workspace` by default (optional per-key override) — see [folders-and-paths.md](folders-and-paths.md) |
| `models` | AI model per stage (`clarify`/`clarify_apply`/`plan`/`implement`) — see [ai-models.md](ai-models.md). `clarify_apply` covers `clarify --apply`/`--auto-answer`/the apply half of `--finalize`, and is a full stage with its own `backends`/`reasoning_efforts` entry too — its optimal backend/effort isn't necessarily the same as `clarify`'s |
| `backends` | CLI backend per stage (`claude`/`copilot`/`codex`) — see [ai-models.md](ai-models.md). Whether each backend is currently *usable* (installed + workspace writable) is checked live, not stored here — see [cli-availability.md](cli-availability.md) |
| `reasoning_efforts` | Reasoning effort per stage (`""` = no override); must be supported by that stage's backend+model — see [ai-models.md](ai-models.md) |
| `features_per_session` | Max features per session (`null` = no limit; default `3`) — dashboard Settings → Runs tab → "Features per Session" |
| `resume_implementation_sessions` | Whether a continuation/require_fixing implementation session should `--resume` the epic's previous session — reusing the context it already paid to build (the epic spec, the code it already read) — instead of always starting cold (default `true`). Escape hatch for the rare case where resuming misbehaves for a given backend/workspace; read fresh via `get_resume_implementation_sessions` in `check_and_run` |
| `commit_after_qa_pass` | Dashboard Settings → Runs tab toggle (default `true`). When an epic's QA verdict lands as a genuine pass (`status == "done"`, `qa_passed == true`, `qa_status == "done"`), `run_qa_session` (`tempa_session.py`) runs `git add -A` + `git commit` in `workspace.root` via `tempa_git.commit_workspace_changes`, so a large unattended run leaves a checkpoint per verified epic instead of one giant uncommitted diff at the end. Read fresh via `get_commit_after_qa_pass` right after each QA session finishes. Skipped silently (logged, not an error) if the workspace isn't a git repo or there's nothing to commit; a real git failure (e.g. no `user.name`/`user.email` configured) is also just logged, never fails the run or sends a notification |
| `max_session_run` | Max sessions per epic (anti-loop safeguard; default `30`) — dashboard Settings → Runs tab → "Max Session Runs" |
| `max_clarification_run` | Max rounds for the `clarify --finalize` loop (default `20`) — dashboard Settings → Runs tab → "Max Finalize Clarification Round". Read **once**, when the finalize run starts (`run_clarify_finalize` in `tempa_clarify.py`): a running loop keeps counting toward the limit that was in effect when it began, even though it re-reads the rest of config.json every round. Changing the value therefore applies from the *next* finalize run onward — nothing needs restarting, since every run is a fresh process. Saving a new value from dashboard Settings while a finalize run is in progress returns a `warning` on `/api/config/save` saying exactly that (`_finalize_limit_change_warning` in `dashboard_runs.py`) |
| `finalize_no_progress_rounds` | Convergence guard for the `clarify --finalize` loop (default `5`) — dashboard Settings → Runs tab → "Max Finalize No-Progress Round". If this many evaluate rounds in a row fail to reduce the critical+major finding count, the loop stops on its own instead of continuing to `max_clarification_run` — the remaining findings likely need a human decision (see `answer`) rather than more automated apply passes. Raise it to give the automation more attempts before it gives up. Snapshotted at finalize-run start exactly like `max_clarification_run` above, and covered by the same `/api/config/save` warning |
| `finalize_checkpoint_rounds` | How many answering rounds of a `clarify --finalize` run may pile up in the pending overlay before the loop stops to write them into the PRD and commit (default `3`) — dashboard Settings → Runs tab → "Checkpoint Every N Rounds". Finalize otherwise touches nothing until the closing compaction (see [clarify-modes.md](clarify-modes.md)), which is cheap but means a long unattended run holds hours of agent work in an overlay the PRD has never seen, with no restorable point until the last step. A checkpoint buys some of that back: `_run_checkpoint` in `tempa_clarify.py` runs one apply pass, then commits (`finalize_checkpoint_commit` below), leaving a readable per-round diff of how the PRD actually changed. `null` (blank in Settings) disables checkpoints entirely and restores the pre-checkpoint behavior; a **missing** key is a config.json written before this setting existed and gets the default. Counted per *answering* round, not `run_number % N` — the counter resets after any write to the PRD (a checkpoint or the closing compaction), so a checkpoint never fires to apply a single round's answers right after a compaction already emptied the overlay. Checkpoint applies deliberately do **not** consume the two-rewrite `MAX_COMPACTIONS` budget, which bounds only the "verification came back dirty, rewrite again" loop — otherwise a run checkpointing every 3 rounds could never reach its 20th. Snapshotted at finalize-run start exactly like `max_clarification_run` above, and covered by the same `/api/config/save` warning. Each checkpoint costs one extra agent session, so `1` (apply after every round) is the most expensive setting here |
| `finalize_checkpoint_commit` | Dashboard Settings → Runs tab toggle (default `true`). At each checkpoint, and at the end of a successful `clarify --finalize` run, `git add -A` + `git commit` in `workspace.root` via `tempa_git.commit_workspace_changes` — the same helper `commit_after_qa_pass` above uses, with the same whole-workspace staging. **What that actually captures depends on the `.gitignore`**: the PRD lives under `.tempa/`, which `tempa init` git-ignores wholesale, so without help `git add -A` would stage everything in the working folder *except* the documents the checkpoint exists to record. `tempa_git.ensure_prd_tracked` is what fixes that — it writes rules that keep `.tempa/` out of the repo while letting `.tempa/specs/prd/` in (see [folders-and-paths.md](folders-and-paths.md)). `init` writes them when a workspace is created or reopened, and the checkpoint re-checks them immediately before committing so a workspace scaffolded before they existed, and left open since, still gets its PRD committed. Everything else Tempa generates — logs, QA/verify reports, `config.json`, the epic and clarification specs — stays out. Messages are `tempa: clarification checkpoint — round N` and, for the closing one, `tempa: clarification finalized — PRD ready for implementation`. Read fresh at each checkpoint. Skipped silently if the workspace isn't a git repo or there's nothing to commit; a real git failure (e.g. no `user.name`/`user.email`) is also just logged, never fails the run |
| `clarify_overlay_warn_findings` | How many answered-but-not-yet-applied clarification findings may pile up before the dashboard's "Pending resolutions" card suggests compacting them into the PRD with **Apply Answers** (default `25`). A warning only — nothing is ever applied automatically, and carrying a bigger overlay is legitimate; it just makes every evaluation prompt larger. config.json-only (no Settings control) |
| `implement_no_progress_rounds` | Convergence guard for a resumed `tempa implement` epic session (default `2`): if this many resumed sessions in a row finish successfully (exit code 0) without `completed_features` increasing, the epic has stopped moving — often because it is blocked on something outside itself (e.g. a dependency owned by a not-yet-implemented epic), which a backend CLI that keeps exiting 0 while explaining it's stuck would otherwise burn all the way to `max_session_run` retries to surface. If the epic's own feature bookkeeping actually shows it's fully complete (`_epic_genuinely_complete`), this is instead treated as a QA-state bookkeeping desync and the epic is automatically repaired and routed back through the QA gate rather than failed. A round that ended by promising to come back with a result Tempa itself then terminated earns the epic one extra round, recorded as `cut_short_rounds`, and is reported as what it was rather than as a blocker; otherwise it's marked `failed` instead of being resumed again. When the session never named an epic it was blocked on, the halt says only that — it no longer asserts a blocker outside the epic it has no evidence for. The session's own explanation is captured into that epic's `blocked_reason` and shown in the dashboard Status tab and `tempa status` |
| `qa_loop_strikes` | Convergence guard for an epic cycling through the QA gate (default `2`). Every QA verdict is appended to that epic's `qa_history` (see `epic` below); a round that shows either a **regression** (a feature that failed QA, was fixed, was re-verified, and is failing again) or a **cycle** (this round's failing features are the same set an earlier round reported, with a different set in between) counts as one strike, and this many strikes in a row marks the epic `failed` with a round-by-round explanation in `blocked_reason`. A passing round clears the count. More than one strike is required on purpose: the QA agent is an LLM, so a single repeat can just be a round that tested more thoroughly than the one before it. Without this guard, a "QA fails features 1-2 → fix → QA fails 3-4 → fixing those regresses 1-2" cycle is invisible to every other safeguard — `implement_no_progress_rounds` is only evaluated while an epic is still `on_progress`/`require_fixing` after a session (a successful fix round sets it `done`), and `total_run` is reset by the forward progress each round makes — `max_session_run` bounds a run of consecutive zero-progress sessions only, and is not a lifetime cap. Settings → Runs tab → "QA Loop Strikes" |
| `max_qa_fail_rounds` | Backstop for the same guard (default `6`): this many failed QA rounds for one epic since the last reset, whatever the pattern, marks it `failed`. `qa_loop_strikes` above fingerprints each round by the per-feature statuses the AI agent writes, and nothing enforces that it writes them (the same class of slip `reconcile_qa_passed_features` exists to repair) — when it doesn't, every fingerprint is empty and the pattern rules correctly refuse to guess. This is what guarantees the loop terminates anyway. Counts only failures, and only ones after the newest `reset` marker in `qa_history`. Settings → Runs tab → "Max QA Fail Rounds" |
| `usage_limit_retry_wait_sec` | Seconds to wait before automatically retrying a clarify/implement/QA/verify step after the configured backend's subscription/token usage limit is hit (default `1800`, 30 minutes) — dashboard Settings → Runs tab → "Retries & Timing" → "Usage Limit Retry Wait". Read fresh via `load_config()` on every wait (`tempa_session.wait_out_usage_limit`), so a change reaches an already-running wait on its next check — no restart needed |
| `usage_limit_heartbeat_sec` | Seconds between "still waiting" heartbeat log lines during the usage-limit wait above (default `300`, 5 minutes) — dashboard Settings → Runs tab → "Retries & Timing" → "Usage Limit Heartbeat Interval". Same fresh-read, no-restart behavior as `usage_limit_retry_wait_sec` |
| `server_overloaded_retry_wait_sec` | Seconds to wait before automatically retrying after the backend's API reports itself overloaded, e.g. a transient 529 (default `300`, 5 minutes) — dashboard Settings → Runs tab → "Retries & Timing" → "Server Overload Retry Wait". Same fresh-read, no-restart behavior, via `tempa_session.wait_out_server_overload` |
| `backend_background_wait_sec` | How long a backend CLI waits for the background work a session's turn left running — a delegated sub-agent, a `run_in_background`/`nohup ... &` command — before killing it and exiting (default `3600`, 1 hour). Applied as an environment default on every spawn (`tempa_session._backend_env`), converted to whatever unit that CLI's own variable takes: Claude Code's `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS`, whose own default is only 10 minutes — routinely less than one feature's implementation takes, so a productive session got killed mid-flight, exited 0, and counted as a no-progress round toward `implement_no_progress_rounds`. Copilot and Codex expose no documented equivalent and are left untouched. `0` means "wait indefinitely" (the CLI's own documented value) and is deliberately not the default, since a session that leaves a dev server running would then hang the runner with no upper bound. A value you export yourself always wins — Tempa only fills the variable in when it isn't already set. Should the ceiling be hit anyway, Tempa recognizes the CLI's own "terminating" message and leaves that round out of the no-progress count instead of failing the epic over it. That recognition covers only background work the CLI's own harness tracks: a shell the session backgrounds through its Bash tool is not governed by it, prints no marker, and is cleaned up by `terminate_leftover_processes` instead — which is the case the cut-short grace under `implement_no_progress_rounds` covers. Note also that this is an unbounded blocking wait for the runner, so a large value is not free; and Tempa now warns when the ceiling the CLI reports disagrees with the configured value, because the variable is a vendor-owned name Tempa can only set as a default. config.json-only (no Settings control) |
| `terminate_leftover_processes` | Dashboard Settings → Runs tab → "Process Cleanup" toggle (default `true`). Terminate whatever a backend CLI session left running when that session ends — the dev server it started to check its own work, a file watcher, a build daemon, a test runner — instead of orphaning it to the OS. Each session's CLI is spawned inside a container the operating system tears down along with it (a Job Object on Windows, a process group on Linux/macOS — see `tempa_process_group.py`), so the session's whole process tree goes, not just the CLI process. It never asks what a process *is*, only who started it, which is what makes it work identically for any toolchain rather than needing a per-language list. This exists because agent CLIs start long-running commands routinely and don't reliably stop them: in one workspace a `vite` dev server was still holding its port 5.4 hours after the session that started it had finished, alongside 15 idle build workers holding 1.9 GB between them. Complements `backend_background_wait_sec` above rather than replacing it — that is how long the CLI itself waits for the background work *it* is tracking before killing it and exiting, and it only helps while the CLI is still alive to act; this covers whatever is still running once the CLI process is gone, including what it never tracked. Scope is what the OS still counts as part of that session: something genuinely detached — a Docker container, an installed service, a job on another machine — is not something Tempa can reclaim. **Platform difference worth knowing:** on Windows the kernel tears the tree down when Tempa's handle closes, so it holds even if Tempa is killed outright; on Linux/macOS it relies on Tempa's own SIGINT/SIGTERM/`atexit` handlers, so a `SIGKILL` of Tempa still leaks the group. Read fresh via `get_terminate_leftover_processes` immediately before each spawn (`tempa_session._stream_backend_process`) and fixed for that process tree's lifetime — so, unlike the `usage_limit_*` waits above, a change never reaches a session already running: it applies from the next session spawned, which during an `implement` run is normally the next epic or QA round. Nothing needs restarting either way. Containment that can't be established is logged and the session continues uncontained — cleanup never fails a run. Turn it off only if you want a session's processes to outlive it (e.g. you intend to keep using the dev server it started); nothing else will clean them up |
| `poll_interval_sec` | Seconds between `tempa implement`'s scheduler checks for new work while idle (default `60`) — dashboard Settings → Runs tab → "Retries & Timing" → "Implementation Poll Interval". Re-read every poll cycle in `tempa_implement.main`'s loop, so a change reaches an already-running agent runner on its next poll — no restart needed |
| `last_clarification_findings` | Summary of the last clarification findings (critical/major/minor) |
| `last_clarification_action` | Which kind of clarification pass ran most recently: `"evaluate"` (`clarify`, or one evaluate iteration of `clarify --finalize`) or `"apply"` (`clarify --apply`, saving in the answer UI, or one apply iteration of `--finalize`). Absent until clarification has run at least once — stamped in `tempa_clarify.py`. Both readiness gates depend on it: its mere presence is the "clarification has been run" condition for Finalize *and* Start Implementation (see `implementation_start_requirement` below), and Finalize additionally wants it to be `"evaluate"`, since an apply pass edits the PRD without re-checking what's left. The combined `tempa clear` removes it (`_reset_clarify_config_state` in `tempa_maintenance.py`) so a wiped workspace reads as never-clarified instead of pointing at runs whose files are gone; plain `clarify --clear` deletes only the files and leaves config.json alone |
| `last_clarification_round` | Running total of every evaluate pass ever (`+= 1` on each one, manual `clarify` or one iteration of `clarify --finalize` alike) — shown on the dashboard as "Round N" next to "Finalize readiness". Unbounded: manual `clarify` isn't limited by `max_clarification_run`, so this is never compared against it |
| `last_finalize_round` | The `clarify --finalize` loop's own in-run counter (`run_number` in `run_clarify_finalize`) — reset to `0` at the start of every finalize run and counted up to `max_clarification_run` within that one run only, independent of `last_clarification_round` above. Shown on the dashboard as "N / M" next to the "Finalized Clarification" / "Stop Finalize" button, refreshed live every second while a run is in progress (`/api/clarify/run`'s poll response) |
| `last_finalize_phase` | Which kind of round a `clarify --finalize` run is on: `"evaluate"` (still finding and answering) or `"verify"` (the closing evaluation over the freshly-compacted PRD). Surfaced by `/api/clarify/run` so the dashboard's round badge can say which is which — a finalize run ends with a verification pass that would otherwise look identical to any other round |
| `last_auto_answer` | Number of findings answered by the last `clarify --auto-answer` |
| `last_clean_evaluation_at` | Epoch timestamp of the most recent fresh evaluate pass that found zero findings across every severity (`0` if none yet). Such a pass leaves no new clarification file behind (there's nothing to write), so the finalize/implement readiness gates fall back to this timestamp — see `_latest_evaluation_findings` in `dashboard_clarify_parse.py` — to recognize a genuinely clean round instead of misreading a stale, older finding-bearing file as still current |
| `allow_finalize_with_critical` | Dashboard Settings → Guardrails tab toggle (default `false`). When `true`, "Finalized Clarification" is allowed to start even while critical findings remain open, letting its automated evaluate/apply loop attempt to resolve them unsupervised. Independent of `implementation_start_requirement` below — this only ever affects Finalized Clarification |
| `skip_minor_findings` | Dashboard Clarification-page toggle + CLI `--skip-minor` (default `true`). When `true`, Start Clarification / Finalized Clarification evaluation passes only look for critical and major findings — minor findings are skipped entirely |
| `implementation_start_requirement` | Dashboard Settings → Guardrails tab → "Start Implementation requires" control — one of `"no_critical_or_major"` (default: zero critical and zero major findings in the most recent evaluation), `"no_critical"` (zero critical findings only; major findings may remain open), or `"none"` (no clarification-findings condition; clarification must still have been run at least once). Enforced both client-side (Home/Clarification/Implementation pages) and server-side in `_handle_implement_run_start` |
| `clarify_applied_hashes` | Per clarification file, a hash of the exact content that was last applied to the PRD/spec (`{filename: content_hash}`). A fully-answered file whose current hash still matches is shown as "✅ Applied" in the dashboard's Clarification overview; a mismatch (or a missing entry) means its answers haven't reached the PRD yet, which is what enables the **Apply Answers** buttons and what the dashboard's apply loop keeps re-running `clarify --apply` for until nothing is left. This is also what an apply pass uses to decide WHICH clarification files to even read — only ones not yet reflected here (the "apply backlog"), never every clarification file ever written — so apply's input doesn't grow with the number of past rounds. **Two further things derive from it**: the pending-resolution overlay carried into every clarification evaluation (every answered finding in a non-matching file — see [clarify-modes.md](clarify-modes.md)), and the **Start Implementation** gate, which requires that overlay to be empty so implementation never reads a PRD missing decisions that were already made. Cleared by `tempa clear` alongside `last_clarification_action` above |
| `clarify_session_id` / `clarify_session_backend` | The most recent clarify EVALUATE session's resumable id + the backend that produced it. An apply pass right after it (same process, e.g. inside `clarify --finalize`) resumes this session instead of starting cold — the evaluate session already paid to read the whole PRD. Only usable if the `clarify_apply` stage's backend matches `clarify_session_backend` (a session id is meaningless to a different CLI) — since `clarify` and `clarify_apply` can now be configured with different backends, this is checked against `backends.clarify_apply`, not `backends.clarify`. Backend-tagged the same way as epic session ids (see `epic` below); cleared by `tempa clear` |
| `clarify_apply_session_id` / `clarify_apply_session_backend` | The apply session's OWN most recent (possibly still-partial) attempt's resumable id + backend — distinct from `clarify_session_id` above. If a usage-limit/overload retry interrupts an apply session mid-run, the retried attempt resumes THIS session instead of losing that attempt's progress and falling back to resuming evaluate (or starting cold) again. Cleared once the apply step it belongs to succeeds, and by `tempa clear` |
| `clarify_file_timings` | Per clarification file, how long its evaluate pass took and how long its most recent apply pass took (`{filename: {clarify_seconds, apply_seconds}}`) — shown in the dashboard's clarification row detail dialog |
| `notifications.email` | Optional SMTP provider/settings and selected attention event names. Username/password may be saved locally in the workspace config or supplied through `TEMPA_SMTP_USERNAME` / `TEMPA_SMTP_PASSWORD`; see [email-notifications.md](email-notifications.md). |
| `epic` | Array of state for every epic (status, features, QA, session_id, etc.). Each entry also carries `qa_history` — one record per QA verdict (`round`, `verdict` = `pass`/`fail`/`reset`, the `failed` feature ids, the `report` path, `at`), capped at the newest 8 — plus its `qa_loop_strikes` counter; together they are what the QA loop guard reads (see `qa_loop_strikes` above). `tempa implement --reset-failed` and `--reset-qa` do **not** delete the history: they append a `reset` marker, which restarts the guard's window while keeping the record of what happened. Each entry's resumable session ids are tagged with the backend that produced them (`session_id`/`session_backend` for implement, `qa_session_id`/`qa_session_backend` for QA) — a stage's backend switching mid-epic starts fresh instead of resuming a foreign CLI's session id. Configs from before multi-backend support (bare `claude_session_id`, no `*_backend` companion) are treated as backend `claude`. Three further runner-owned fields relate to rounds Tempa itself cut short: `last_round_note_kind` labels what kind of thing `last_round_note` is (`unfinished_check` = a promise to come back whose object was terminated, so the next round is told to redo the check rather than treat the note as a claim about the code); `cut_short_rounds` is the one-round allowance such a round earns, dropped as soon as a feature completes and cleared by `--reset-failed`; `ended_waiting_halts` counts how many times the epic has halted that way and deliberately SURVIVES `--reset-failed`, since Continue Implementation runs the reset itself and nothing else could tell the first halt of that shape from the tenth. All three are restored after every session (`_RUNNER_OWNED_EPIC_KEYS`), so an agent rewriting its own entry cannot grant itself grace |

Prompt templates are **no longer** in config.json — see [prompt-templates.md](prompt-templates.md).
Architecture principles aren't in config.json either: they live in
`.tempa/architecture-principles.md` — see
[architecture-principles.md](architecture-principles.md).

## Files that live beside config.json

| Path | What it is |
|---|---|
| `.tempa/config.lock` | Held for the duration of a read-modify-write that comes from outside the runner (currently: answering a blocked feature's decision from the dashboard). Created and deleted around the write; a lock file older than 30 seconds is assumed to belong to a process that died holding it and is broken. Safe to delete by hand if one is ever left behind. |
| `.tempa/decisions/<EPIC>__<FEATURE>.json` | A decision answered from the dashboard, recorded before it is written into `config.json` and re-applied by the runner on every poll until the epic has moved on — so an answer can't be lost to another writer saving a stale copy of `config.json` over it. Deleted automatically once it has been acted on. See [start-implementation.md](start-implementation.md#decisions-only-you-can-make). |
| `.tempa/graceful-stop-implement`, `.tempa/graceful-stop-clarify` | Sentinels for **Stop After Current Session**. Presence is the whole message. |
