Architecture Principles

The rules your project always follows — written once, applied by Tempa to every single thing it does.

What they are

Architecture Principles are the standing decisions that apply to your whole project, not to one feature. Things like which database you use, whether you allow an ORM, how errors are returned from an API, or what has to be true before code is considered done.

They are the answers you would otherwise have to repeat in every conversation. Instead of explaining "remember, we don't use an ORM" in each specification, you write it down once here, and Tempa carries it into every stage on its own.

Why they matter in Tempa

Tempa runs your project through several separate AI sessions: clarification, applying answers, planning epics, implementing features, QA, and verification. Each one is a fresh session — it does not remember the previous one.

Your Architecture Principles are prepended to every one of those prompts, automatically. That is the whole point: the same rules are in force whether Tempa is asking you a clarifying question, drafting a plan, writing code, or reviewing that code in QA. Without them, each stage falls back on generic defaults, and you get an application that is internally inconsistent — one service using an ORM, another hand-writing SQL, because nobody ever said which one to use.

They are treated as non-negotiable. Tempa tells the AI that these principles outrank convention, convenience, and its own defaults — and that if a principle conflicts with your specification, it must stop and report the conflict rather than quietly pick a side. That means a bad principle is enforced just as strictly as a good one, so it is worth writing them carefully.

Completely optional

You can leave this empty and go straight to Step 1 (Upload Specification). Tempa works exactly as it did before — nothing is injected, and no prompt changes. Add principles when you have project-wide decisions worth locking in.

What belongs here — and what doesn't

Belongs hereDoes not belong here
Rules that hold true for the entire project Requirements for one specific feature — those go in the specification
Technology choices and versions you have committed to Things you are still undecided about — leave those to clarification
Quality bars that every change must clear A task list or roadmap — Tempa generates those from the specification
Constraints that come from outside the code (compliance, contracts, existing systems) Long background essays or business context — that is specification material
Conventions that would otherwise drift between sessions Anything that changes every sprint — principles should be stable

How to write good ones

1. Be specific enough to check

A principle should be something you could point at a pull request and say "this passes" or "this fails".

Too vague: Write clean, high-quality code.
Checkable: No function longer than 50 lines. No file longer than 400 lines. Extract rather than nest past 3 levels of indentation.

2. Say what to do, not just what to avoid

A prohibition leaves the alternative undefined, and the AI will invent one.

Incomplete: Don't use an ORM.
Complete: Don't use an ORM. All database access goes through hand-written SQL in a repository class, one file per aggregate.

3. Include the reason when it isn't obvious

A stated reason lets the AI judge edge cases instead of applying the rule mechanically — and tells it when to flag a conflict rather than guess.

Better: All timestamps are stored in UTC and converted only at the presentation layer. We operate in three time zones and have been burned by mixed-offset data before.

4. Keep them stable

If a rule will change next month, it is a task, not a principle. Principles are what you would still say a year from now.

5. Keep the list short

Ten to thirty sharp principles beat a hundred vague ones. A long list dilutes the important rules and increases the chance of two principles contradicting each other.

6. Don't contradict yourself

Tempa enforces every principle. Two rules that cannot both be satisfied will produce a stream of reported conflicts instead of progress. Read the list end-to-end after editing it.

Examples by category

Use these as a starting point — copy what fits, delete what doesn't, and replace the specifics with your own.

Technology stack

  • Backend is Python 3.12 with FastAPI. Do not introduce a second web framework.
  • Frontend is React 19 with TypeScript in strict mode. No new JavaScript files.
  • PostgreSQL 16 is the only datastore. Do not add Redis, Elasticsearch, or a message queue without flagging it first.
  • Package management is uv for Python and pnpm for Node. Do not commit a package-lock.json or requirements.txt.
  • No new third-party dependency for something the standard library already does well.

Code organization

  • Each service lives in its own folder under src/ and owns its own database schema. Services never read each other's tables — they call each other's APIs.
  • Business logic lives in the domain layer and must be testable without a database or an HTTP server.
  • No circular imports between modules. If two modules need each other, the shared piece moves to a third module.
  • One public class or function per file for anything over 50 lines.

Data and persistence

  • Every schema change ships as a numbered, forward-only migration. Never edit a migration that has already been merged.
  • All database access goes through a repository class. No SQL in route handlers or in the domain layer.
  • Timestamps are TIMESTAMPTZ and always stored in UTC.
  • Money is stored as integer minor units (cents), never as a float.
  • Deletes are soft by default: set deleted_at, don't remove the row.

API design

  • REST with JSON. Resource paths are plural nouns; actions are HTTP verbs, not path segments.
  • Errors always return the same shape: {"error": {"code": "...", "message": "...", "details": {...}}}. Never leak a stack trace or a raw database error.
  • Every list endpoint is paginated with limit and cursor. There is no unbounded list endpoint.
  • Breaking changes require a new version prefix. Existing endpoints stay backward-compatible.
  • Every request and response body is validated against an explicit schema at the boundary.

Security

  • No secret is ever committed, logged, or included in an error message. Secrets come from environment variables only.
  • Every endpoint is authenticated by default. A public endpoint must be explicitly marked and justified in a comment.
  • Authorization is checked at the service layer, not only in the UI or the route.
  • All user input is validated and parameterized. No string-concatenated SQL, ever.
  • Personal data is never written to application logs.

Testing

  • Every endpoint has at least one integration test that hits a real database — mocked database tests do not count as coverage.
  • Every bug fix starts with a failing test that reproduces the bug.
  • Tests must be independent and runnable in any order. No test depends on another test's leftover data.
  • A feature is not "done" until its tests pass locally.

Performance

  • No N+1 queries. Loading a list of N items must not issue N additional queries.
  • Every foreign key and every column used in a WHERE clause is indexed.
  • Anything that could take longer than 5 seconds runs as a background job, not inside a request.
  • Don't add a cache to hide a slow query — fix the query first.

Observability and operations

  • Logs are structured JSON with a request id. No bare print statements.
  • Every external call has an explicit timeout and a defined failure behaviour.
  • Configuration comes from environment variables with documented defaults. No hardcoded hostnames, ports, or paths.
  • Every service exposes a health endpoint that actually checks its dependencies.

Process and documentation

  • Any decision that is hard to reverse gets an ADR in adr/ before the code is written.
  • Update the docs in the same change as the code, not afterwards.
  • Comments explain why, never what. Delete a comment that only restates the code.

A complete example

This is what a real, usable principles document looks like — short, specific, and opinionated. Yours does not need to be longer than this.

# Architecture Principles — Clinic Back-Office

## Stack
- Python 3.12 + FastAPI for all backend services. No second framework.
- PostgreSQL 16 is the only datastore. Flag any proposal to add another.
- React 19 + TypeScript strict mode on the frontend.
- No new dependency for something the standard library handles well.

## Structure
- One service per folder under src/. A service owns its own tables and
  never reads another service's tables directly.
- Business logic lives in the domain layer and is testable without a
  database or an HTTP server.
- Database access only through repository classes. No SQL in route handlers.

## Data
- All timestamps are TIMESTAMPTZ stored in UTC. We operate across three
  time zones and have been burned by mixed offsets before.
- Money is stored as integer cents, never as a float.
- Schema changes ship as numbered forward-only migrations. Never edit a
  merged migration.
- Deletes are soft: set deleted_at.

## API
- REST + JSON. Plural resource nouns, actions expressed as HTTP verbs.
- Errors always return {"error": {"code", "message", "details"}}. Never
  leak a stack trace or raw database error to a client.
- Every list endpoint is paginated (limit + cursor). No unbounded lists.

## Security
- Every endpoint is authenticated unless explicitly marked public with a
  justifying comment.
- Authorization is enforced in the service layer, not just the route.
- Secrets come from environment variables. Never committed, never logged.
- Patient data must never appear in application logs. This is a
  regulatory requirement, not a preference.

## Quality
- Every endpoint has an integration test against a real database.
  Mocked-database tests do not count.
- Every bug fix begins with a failing test that reproduces it.
- No function over 50 lines, no file over 400 lines.
- Comments explain why, not what.

Common mistakes

  • Writing the specification here. Principles are how the project is built; the specification is what is being built. Feature requirements belong in the PRD.
  • Being too vague to enforce. "Follow best practices" changes nothing — the AI already thinks it is doing that. Name the practice.
  • Contradicting yourself. "Keep it simple" plus "abstract every external dependency behind an interface" will collide constantly. Decide which one wins.
  • Writing a hundred rules. The important ones get lost. Start with the ten you would actually reject a pull request over.
  • Locking in something you are unsure about. If you have not decided yet, leave it out and let clarification surface the question.
  • Never revisiting them. When a principle stops being true, change it — a stale principle is enforced just as strictly as a current one.

Where they are stored

Your principles are saved as a plain Markdown file inside the working folder you selected:

<your-working-folder>/.tempa/architecture-principles.md

They are per-project, so each working folder has its own set. The file survives Clear All — clearing removes plans, QA reports, logs, and clarification results, never your principles. You can also read the current value from the terminal:

tempa show-principles

Editing is done here in the dashboard.
